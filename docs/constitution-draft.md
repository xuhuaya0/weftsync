## 核心原则

### I. 简单优先（SIMPLICITY FIRST）

**规则**
- 不实现当前不需要的功能（YAGNI）
- 能用标准库解决的不引第三方依赖
- 能一个模块解决的不拆三个
- 不为「将来可能用到」预先抽象
- 复杂度必须有明确收益，否则选简单方案

**为什么**：简单系统易于理解、测试、修改。复杂度会累积利息。

**如何检查**：新增依赖/模块/抽象层时，说明「不用它具体会付出什么代价」。说不出来就不加。

**出处**：KISS / YAGNI（XP 实践）、UNIX 哲学「做一件事并做好」

---

### II. 验证优先于断言（VERIFIED, NOT ASSUMED）

**规则**
任何「已完成 / 已修复 / 已生效 / 不可行」的结论，必须附**可复现的证据**：
命令原文与输出、测试结果、文档原文、或运行时观测值。

禁止以下推断链：
- 「改法看起来对」→ 宣布修好
- 「文件已落盘」→ 宣布产物可用
- 「代码读起来是这样」→ 宣布运行时行为如此
- 「我记得某产品是这样」→ 当成事实引用

**必须验证到实际链路**：配置被加载、函数被调用、产物被消费。

**为什么**：未验证的断言会引发返工，代价远高于多跑一条命令。
外部工具/产品的行为尤其容易记错，必须以文档原文为准。

**如何检查**：结论能否指出具体证据（命令输出 / 测试名 / 文档链接 / 源码行号）。
指不出来的，标为「推测」，不得写进文档的事实章节。

**出处**：经验主义（empirical software engineering）、TDD 红-绿循环

---

### III. 失败要显式，不要静默（FAIL LOUD）

**规则**
- 错误必须被捕获并**明确报告**，不允许吞掉
- 不使用空 `catch` / `except: pass` / `_ = err`
- 不确定的情况宁可报错，不猜默认值继续
- 破坏性操作前先检查前置条件，不满足就拒绝执行
- 日志区分「成功」「跳过（及原因）」「失败」

**为什么**：静默失败是最贵的 bug —— 它让问题在很久之后以更难诊断的形式出现。

**如何检查**：每个错误分支是否有可观测输出（日志 / 返回值 / 通知）。

**出处**：Fail-fast（Martin Fowler）

---

### IV. 单一事实来源（SINGLE SOURCE OF TRUTH）

**规则**
- 同一信息只在一处定义：配置、常量、路径、状态
- 复制粘贴的代码，第二次出现时提取
- 文档里的事实必须与代码/配置一致；不一致时改文档
- 状态只允许一个权威来源，不许两处各记一份

**为什么**：重复信息必然漂移，漂移后无法判断哪个对。

**如何检查**：同一常量/路径/规则是否在多处硬编码。文档事实能否对应到代码。

**出处**：DRY（The Pragmatic Programmer）

---

### V. 边界与最小权限（BOUNDARY & LEAST PRIVILEGE）

**规则**
- 只操作被授权的范围，越界即拒绝
- 申请权限取**能满足需求的最小集合**，不「全量权限省事」
- 凭据不进版本库；不在日志/报错里回显
- 对用户数据做破坏性操作前必须三件齐备：**显式确认 + 快照 + 可撤销路径**

**为什么**：权限与影响范围一旦扩散，事故半径随之扩大；凭据泄露不可回收。

**如何检查**：调用的 API/路径是否都在声明范围内。scope 是否最小。破坏性操作三条保护是否齐全。

**出处**：Principle of Least Privilege（Saltzer & Schroeder, 1975）

---

### VI. 可复现（REPRODUCIBLE）

**规则**
- 产物由脚本生成，不靠手工步骤
- 脚本幂等：重跑结果一致
- 构建/测试能在干净环境里一条命令重现
- 临时产物落在约定位置（本仓库：`.scratch/`），并入库忽略

**为什么**：不可复现的产物无法审计、无法回滚、无法交给别人重做。

**如何检查**：删掉产物目录后能否用仓库脚本完整重建；脚本重跑两次结果是否一致。

**出处**：Reproducible builds、Infrastructure as Code

---

### VII. 渐进交付（INCREMENTAL DELIVERY）

**规则**
- 一次只推进一步，完成即汇报，不一口气做到底
- 大变更拆成可独立验证的小步
- 每步留下可检查的产物（文件 / 测试 / 命令输出）
- 计划写在磁盘上并随进展更新，不只存在对话里

**为什么**：一次性大交付方向错了就全部作废；小步可及时纠偏。

**如何检查**：本次提交能否独立说明「做了什么、如何验证」。`PLAN.md` 是否反映最新进度。

**出处**：迭代开发、持续集成、小步提交

---

### VIII. 改动前先理解（CHESTERTON'S FENCE）

**规则**
- 删除/修改看似无用的代码前，先弄清它为什么存在
- 不理解的代码不重构
- 引用外部产品/标准的行为前先查原文；记忆不算证据

**为什么**：看似冗余的代码往往对应真实约束，移除后才发现时代价最高。

**如何检查**：改动能否说清「原设计要解决什么问题」。外部行为引用是否附了文档/源码位置。

**出处**：Chesterton's Fence

## 项目约束

> 以下不是通用准则，是本项目（weftsync）的具体约束。
> 违反时需在 `plan.md` 的 Complexity Tracking 里说明。

### 平台

- **Windows 为首要目标，Linux 必须同样可用**（R9）。跨平台差异在设计阶段处理，不留到实现时
- 单文件产物优先：`GOOS=windows` / `GOOS=linux` 交叉编译，避免运行时依赖

### 安全（硬性红线）

- **远端仓库是公开的**，任何凭据、token、内部地址不得入库（R10）
- 凭据只从系统凭据库 / 加密文件 / 环境变量读取；配置文件只放引用
- 提交前必须过密钥扫描（`scripts/check_secrets.py`，已挂 pre-commit）

### 技术栈

- Go（rclone 依赖，跨平台单文件）
- Python 仅用于开发辅助脚本（探测、校验），不进产物
- 底层同步引擎复用 rclone，不重写

### 工程约定

- 提交前必须跑测试；测试红了不许提交
- 破坏性操作必须有撤销路径
- PowerShell 5.1 脚本一律纯 ASCII（GBK 解析中文会报误导性错误）
- 终端中文输出的工具应自己写 UTF-8 文件（`--out`），不依赖管道编码

## 开发流程

```
宪法 → spec（做什么）→ clarify（补边界）→ plan（怎么做）→ tasks（拆步骤）→ implement（写代码）
```

### 门禁

| 阶段 | 门禁 |
|---|---|
| **plan** | Constitution Check：逐条对照上面 8 条，违反须在 Complexity Tracking 说明 |
| **tasks** | 每个任务必须有可验证的完成标准 |
| **implement** | 测试通过 + 密钥扫描通过 + 本次改动可独立说明 |
| **交付** | 用户确认，不自行宣布完成 |

### 例外处理

- 违反任一条原则都允许，但必须**写明理由**和**更简单的替代方案为何不可行**
- 未说明理由的违反视为不合规

---

## 治理

- 本宪法优先于其他实践约定；冲突时以本文件为准
- **修订流程**：提出理由 → 记入 `docs/decisions.md` → 改版本号 → 用户批准
- **版本语义**
  - MAJOR：原则增删，或语义反转
  - MINOR：新增条款
  - PATCH：措辞修正
- **效力范围**：本仓库所有 spec / plan / 代码 / 文档
- **复查时机**：每个 feature 的 plan 阶段至少复查一次；原则不适用时按修订流程处理
