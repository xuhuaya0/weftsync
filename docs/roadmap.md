## 每个 Feature 的验收标准

> 「完成」的定义写在这里。达不到就不许标 ✅（宪法原则 II：验证优先于断言）。

### F1 · 飞书后端：只读 + 小文件上传 🔄

**范围**
- rclone 后端注册（`feishu`），`weftsync help backends` 可见
- `NewFs` / `List` / `NewObject` / `Open`（只读）
- `Put`（≤20MB 走 `upload_all`）
- `Mkdir`（`create_folder`）
- 凭据从 `WEFTSYNC_FEISHU_*` 环境变量读取（first cut，正式凭据存储留给 F5/F6）

**验收标准（全部可执行验证）**
1. `weftsync lsf feishu:` 能列出授权文件夹的内容
2. `weftsync copy feishu:<路径> ./local` 能把文件拉回本地，字节内容与云端一致
3. `weftsync copy ./local feishu:<路径>` 能上传 ≤20MB 文件，飞书客户端可见
4. `weftsync lsd feishu:` 能列出子目录
5. 空目录能建（`weftsync mkdir feishu:<新目录>`）
6. 单测覆盖：`List` 解析、路径↔token 映射、错误码分类
7. `Size()` 返回真实值或 -1 的行为已记录（取决于最终策略）
8. 编译产物：Windows + Linux 各一个（`scripts/build-go.ps1 -Target both`）

**实测结果（2026-11-06，真实租户 `_bot_test`）**

| # | 验收项 | 结果 | 证据 |
|---|---|---|---|
| 1 | `lsf` 列目录 | ✅ | 空目录退出 0；有文件时正确列出 |
| 2 | 下载并比对 SHA-256 | ✅ **SC-002** | `AA5B2942...` 两侧完全一致 |
| 3 | 上传后可见 | ✅ | `lsf` 可见，回读内容为 `MODIFIED content v2` |
| 4 | `lsd` 列目录 | ✅ | 输出 `-1 2026-11-06 16:07:33 -1 go-testdir` |
| 5 | `mkdir` 建目录 | ✅ | 建后 `lsd` 可见 |
| 6 | 单测 | ✅ | 20+ 用例全绿，`go vet` 通过 |
| 7 | `Size() = -1` | ✅ 已记录 | research R6 |
| 8 | 双平台产物 | ✅ | Windows 66.2MB + Linux 66.1MB |

| `purge remote:path` 真正删净（含空目录） | ✅ |

**实现过程中发现并修正的问题**
1. rclone 用 `Mkdir("")` 表示「创建 Fs 的 root」→ 原实现直接返回 nil，导致 `mkdir` 静默无效
2. `resolveDir` 忽略了 `rootPath`，把「Fs 根」当成 base folder
3. rclone 把 `remote:dir/file.txt` 当作 root → 需要 `NewFs` 检测并返回父目录 + `ErrorIsFile`
4. 并发列目录惊群：16 个 goroutine 各列一次 → 加 in-flight 合并
5. `fs.ErrorCantUpdate` 不存在（research R8 已修正为「实现 Update，先传后删」）
6. **缓存填充覆盖并发 invalidate**：列表请求在 `createFolder` 之前发出，回来时把陈旧快照写回缓存，
   下一个 `resolveDir` 又报「目录不存在」→ 加入**代际计数**（请求开始时快照 `gen`，返回时 `gen` 已变则不入缓存）
7. **`isNotFound` 后的重试自相矛盾**：失效后立即重查会 join 到同一个陈旧 inflight 请求 → 新增 `listFresh` 绕过缓存与 inflight
8. **`Rmdir` 重复拼 `f.root`**：路径变成 `_inc_test/_inc_test`，子目录永远「directory not found」
9. **`Rmdir` 返回 `ErrorCantRmdir` 让 `purge` 变成 exit=0 的静默 no-op** → 改为「只删空目录」（D18）
10. **错误码三处清单不一致**：`1061001` 加进了 `Retryable()` 却不在 `businessError` 的构造清单里，
    于是永远变成 `UncategorizedError`、永远不会重试 → 合并为单一 `codeTable` + 一致性测试（D20）
11. **并发写 state 抢同一个 `.tmp`**：Windows 上 rename 报「文件被另一进程占用」→ 加 `stateMu` 串行化
12. **`state.New()` 不带路径**：`Save` 报「cannot save a snapshot with no path」→ 新增 `SetPath`

**不做（留给后续 feature）**

**关键设计决策（来自 PLAN.md / decisions.md）**

- state 的锁已实现并测过，但 F1 的 backend 不自动持有（D17）

### F2 · 分片上传 + 限流 + 重试 🔄

**验收**
1. >20MB 文件能上传成功（实测 25MB 走 7 个 4MB 块）
2. 上传后 `Content-Range` 显示的总字节数 = 本地文件大小
3. `--tpslimit 5` 生效，不触发 1061045
4. 限流错误能自动退避重试
5. 上传中断后能续传（`upload_id` 持久化）

**实测结果（2026-11-06，真实租户）**

| # | 验收项 | 结果 | 证据 |
|---|---|---|---|
| 1 | >20MB 上传成功 | ✅ | 20MiB 直传；21MiB → 6 块；60MiB → 15 块 |
| 2 | 总量与本地一致 | ✅ | 三个文件回读 SHA-256 全部 MATCH |
| 3 | 限速：不超 5 QPS | ✅ **默认开启** | 客户端 `rate.Limiter`，默认 5 QPS、burst 1；`--feishu-qps` 可调，0 关闭 |
| 4 | 限流错误能自动退避重试 | ✅ | `1061045` / `1061001` / `1064230` 可重试并退避（1s/2s/4s） |
| 5 | 断点续传 | ⚠️ 改为块级长重试（见下）；`upload_id` 落盘不做 | 见下 |

> **为什么不能靠 rclone 的 `--tpslimit`**：后端用自己的 `http.Client`，不经过 rclone 的
> `fshttp` 传输层，所以 `--tpslimit` 对本后端**无效**；而且它是进程级单一阀值，
> 无法表达「move 是 20/分钟」。详见 D30。

**额外验证**

| 场景 | 结果 |
|---|---|
| 分片大小取自服务端 `block_size` | ✅ 日志显示 `4194304` 来自 `upload_prepare` |
| 分片文件参与增量 | ✅ 二次运行 `skipped=3` |
| 改一个分片文件，其余仍跳过 | ✅ `replaced=1 skipped=2` |
| 替换分片文件不留重复 | ✅ 60MiB→30MiB，远端仍 3 条 |
| `block_num` 与 `block_size` 矛盾时拒绝上传 | ✅ 单测 |
| 源文件比声明短/长 | ✅ 单测：都在 `upload_finish` 前中止 |
| 某块失败就停，不继续发剩余块 | ✅ 单测 || 单块可重试错误 → 原地重试并成功 | ✅ 单测：2 次失败后成功，总调用 4 次（含下一块） |
| 单块永久错误 → 立即失败，不重试 | ✅ 单测：权限错误只发 1 次（不烧配额） |
| 重试预算用尽 → 错误里写明尝试次数 | ✅ 单测：`after 4 attempt(s)` + 24 小时过期说明 |
| 重试等待期间收到停止 → 立即返回 | ✅ 单测：30 秒退避下 5 秒内返回 |
| 25 MiB 真实分片上传仍正确 | ✅ 回读 SHA-256 一致（`632979B2…`） |
**本 feature 额外修掉的真实缺陷（不属于 F2 但被它暴露）**

1. **下载 >8MiB 被静默截断**：`client.do` 的 `maxResponseSize = 8MB`（给 JSON 列表的护栏）
   也套在了下载上，导致 20/21/60MiB 三个文件下载回来都是 8388608 字节且**不报错**。
   已改为流式下载（D22）。这也说明 SC-002 之前判错了——它要求「下载 10MB 一致」，
   而 F1 只跑过小文件。
2. **替换文件时旧版本从未被删除**：`Update` 在 `Put` 之后才去读旧 token，
   而 `Put` 已经把 state 改成新 token，于是「删旧」被无条件跳过。
   **更严重的是它一直被 `lsf` 掩盖**（`List` 折叠同名），所以 SC-009/SC-010
   之前的结论作废（D24）。已加回归测试并验证它会红。

**未做（因此本 feature 未标 ✅）**

| 缺口 | 原因 |
|---|---|
| 全局限速 5 QPS | 官方对 `upload_*` 三个接口都限 5 QPS / 10000 每天；现在靠「出错后退避」而不是「事先不发超」 |
| 并发分片 | 官方明说不支持并发调用，故意不做（D21） |

**断点续传：只做到块级，不做 `upload_id` 落盘（2026-11-08，详见 D45）**

块级长重试已实现：一块可重试失败时最多再试 4 轮（2s/4s/8s/16s 退避），
遇到永久错误立即失败。这吃掉的是「传 1GB 到第 200 块时网断了」这类最常见的损失。

`upload_id` 落盘（跨进程续传）**不做**，理由是它依赖一个不存在的能力：
Feishu 只有 `upload_prepare` / `upload_part` / `upload_finish` 三个端点，
**没有任何一个能告诉你「已经收到哪些块」**。落盘的 `upload_id` 重启后只能
从第 0 块重传，等于把「重传整个文件」改名为「续传」。

真正需要续传的场景是「大量小文件传一半中断」，那个已经被 state 增量同步覆盖：
重跑只传没传完的。

### F3 · 删除 / 更新 / 移动 + 删除保护 ✅

**验收**

| # | 验收项 | 结果 | 证据 |
|---|---|---|---|
| 1 | `deletion = permanent` 删除后云端文件消失 | ✅ | `_f3perm` 只剩 1 个在册文件，无回收目录 |
| 2 | `deletion = versioning` 落到 `_weftsync_trash/<时间戳>/` | ✅ | `_trash/20261107-171809/` 内含 2 个被删 + 1 个被覆盖的文件，回读字节 MATCH |
| 3 | 待删超过 `max_delete` 时整轮中止、一个都不删 | ✅ | 6 个待删 / 上限 2 → exit 1，远端 7 个文件**一个不少** |
| 4a | `variant = update` 只增不减 | ✅ | 远端独有文件保留；`max_delete = 0` 也不报错 |
| 4b | `variant = mirror` + 删除 | ✅ | 恰好 2 个待删 / 上限 2 → 放行并删掉 2（边界不差一） |
| 4c | `variant = two-way` / `custom` | ✅ two-way 已实现（F9）/ `custom` 明确报错 | two-way 真实租户 8/8，见 F9 |
| 5 | 熔断时通知 | ✅ | 托盘气泡 + 日志 `notify:` 行；实测失败运行 1 条、成功 0 条（D42） |
| 6 | 服务端 `Move` | ✅ | `moveto` 后文件确实进入子目录；token 不变；单测覆盖跨 root 场景 |
| 7 | `--plan` 只报告不改动 | ✅ | 报告 `deleted=3`，远端文件数不变 |

**设计要点（详见 `docs/decisions.md`）**
- `max_delete` 是**两轮**闸门：预检轮（dry-run，照常计数但不删）+ 执行轮（D25）
- rclone 自带的 `--max-delete` **语义相反**（删到上限再停），实测确认，不能直接用
- `versioning` 复用 rclone 的 `--backup-dir`，因后端实现了服务端 `Move` 而不产生流量（D26）
- 回收目录必须排除出同步集，用 `filter.AddConfig` 追加规则（D28）
- sync 层独立成 `job` 包，backend 只管单文件（D27）
- 作业文件格式见 `docs/job-file.md`

**本 feature 修复的真实缺陷**
1. **`Move` 的两个路径坐标系搞混**：目标 Fs 的 root 与源 Fs 的 root 不同（`moveto` 的
   典型情况），直接比较 `remote` 和 `src.Remote()` 导致永远判定为「无需动作」，
   命令却报 `Moved (server-side)`。同一个缺陷还让 `versioning` 失效并制造同名副本。
2. **`filter.NewFilter` + `ReplaceConfig` 会让所有文件都不参与同步**（D28）。

**F1 遗留进来的一项：清理同名重复副本 ✅ 已完成**

降级模式（state 丢失/损坏）会全量重传，云端因此出现同名重复副本（D19 有完整背景）。
问题不是「不知道要不要删」，而是**根本删不到**：`Fs.List` 把同名条目折叠成一条，
其余副本对 rclone 完全不可见。

实现为后端命令（D29，用法见 `docs/backend-commands.md`）：

| 命令 | 作用 |
|---|---|
| `backend duplicates` | 列出同名重复，不改动 |
| `backend dedupe -o confirm=true` | 删除非快照记录的副本 |

拒绝删除的三种情况：无 `state_file` / repair 模式 / 记录的 token 不在目录里。
不做「保留最新」这类启发式（多机同步时会删掉别人刚传的新版本）。

验收实测：造 3 个同名副本 → 保留快照记录的 token、删掉 2 个、剩 1 个；
不带 `confirm` 时一个不删；无 state 时拒绝。

**未做（因此本 feature 未标 ✅）**

| 缺口 | 原因 |
|---|---|
| 作业文件里配 `state_file` | ✅ 已支持：`[pair.remote.options]`（只允许非敏感项，凭据会被拒绝） |

`two-way` 已于 2026-11-08 实现（F9 第一期），`custom` 仍明确报错 ——
它不是「没来得及做」，而是「没想清楚要不要做」：自定义矩阵有 9 个方向的组合，
每个组合都需要独立的闸门设计，现在做只会得到一个没人敢用的开关。

**熔断通知 2026-11-08 已实现**

`--tray` 启动成功后 daemon 才安装通知回调，于是在无人值守的定时运行里，
**失败 / 被闸门拦下 / 有冲突** 三种情况会弹托盘气泡；**成功、预览、用户手动停止不弹**。
通知同时写一行 `notify: <标题>` 到日志 —— 气泡会消失，日志得能回答「有没有被告知过」。

实测：不存在的本地目录 → 日志出现 `tray: icon shown` 与 `notify: weftsync：bad 同步失败`，
且没有 `tray notify:` 报错（说明 Win32 接受了这个气泡）；正常目录跑一轮 →
上传成功且 `notify:` 行数为 **0**。详见 D42。

**`max_delete_size`（按体积限）2026-11-08 已实现**

原因里曾写着「rclone 没暴露 `deletesSize`」—— 确实没有读接口（`deletesSize` 不导出，
也不在 `RemoteStats` 里）。做法改成借用 rclone 自己的阈值：只在**预检的那一趟**打开
`--max-delete-size`，它的检查发生在真正删除之前，所以触发时什么也没删。

判定方式不靠字符串匹配：预检报错时**关掉上限再测一次**，如果这趟能跑完且统计到的
待删数更多，就说明拦住它的是体积上限；如果照样失败，那就是真的失败，原样报出。

验收实测（local 后端，4 个 1 KiB 文件 / 只有 4 个待删）：

| 配置 | 结果 |
|---|---|
| `max_delete_size = "1k"` | `BLOCKED`，exit 1，文案「wanted to delete 4 file(s), more than max_delete_size allows (1 KiB). **NOTHING was deleted**」，远端 4 个文件一个不少 |
| `max_delete_size = "1M"` | 正常删除 4 个，远端 0 个，exit 0 |
| `max_delete_size = "1 kilobyte"` | 加载阶段就被拒，错误里点名该字段 |

界面：作业级与 pair 级都多了「删除体积上限」输入框，留空=不限；改 750M → 2G 经 API
往返正确，写入 `max_delete_size = "2G"`；填 `lots` 被 400 拒，文件保持不变。

**已知局限**：只有预检那一趟按体积限。真跑那一趟不设上限（否则就变成「删到上限再停」
的局部删除，正是本项目拒绝的语义），所以「两趟之间目标端被外部改动」这种情况
只能靠文件数上限事后发现，字节数不复查。

**凭据存储：为什么不上 keyring（2026-11-08）**

原验收写的是「凭据走 Linux 加密文件路径」。实际结论是**不上 keyring，但把威胁模型说清楚**：

| 问题 | 事实 |
|---|---|
| rclone 的「模糊」是什么 | **混淆，不是加密**。固定算法、无密钥，能读到文件就能还原 |
| 那 0600 有什么用 | 防「同机器其他用户」和「误同步到云盘」。实测（ext4，6/6）：保存后文件从 644 变 600，密钥不以明文存盘 |
| 为什么不接 libsecret | 需要 D-Bus + Secret Service；WSL 无，服务器无，容器里也无。引入 cgo 依赖会破掉「静态单文件二进制」这个特性 |
| 那真正的防护靠什么 | 操作系统级磁盘加密（BitLocker / LUKS / FileVault）。界面上已经写明这一点，不假装有加密 |

> 这一项必须用 ext4 测，不能用 `/mnt/c`：DrvFs 上权限一律显示 777，
> 写反了就会得到「永远 PASS」的假结论。脚本里现在会先检查文件系统类型。

**Linux 专属路径覆盖**：`pid_unix.go`（`syscall.Kill`）通过 `state` 锁被实际执行；
`os.Rename`、`O_EXCL` 行为验证通过。

**本轮修掉的两个真实缺陷（详见 D32）**
1. **反斜杠被无条件当作路径分隔符** —— Linux 专属缺陷。`weird\name.txt` 被上传成
   `weird/name.txt`，等于访问了另一个路径。改为平台感知的 `filepath.ToSlash`。
2. **没有 `state_file` 的 pair 整体失败** —— 冲突检测把「没有基线」当成错误，
   而没配 `state_file` 是**默认配置**，等于让最常见的情况不可用。

**未做 / 局限**

WSL 不是真机：内核是微软的，磁盘可能是 DrvFs。上述结果证明「Linux 二进制在这套内核上
行为正确」，**不能替代独立发行版实机验证**（尤其 systemd 集成与桌面环境的开机自启）。

`/mnt/c` 上的权限一律是 777，所以凡涉及权限的验证（state 文件 0600、凭据文件 600）
都必须在 `$HOME`（ext4）下跑，脚本里现在会先检查文件系统类型再决定要不要继续 ——
写反了会得到「永远 PASS」的假结论。

**实现要点**：
- 后端 `conflicts` 额外返回 `matched`（token 未变的路径）与 `remote_added`（快照里没有的文件）。
  `matched` 是判断「本地删了」的唯一途径：本地文件系统 backend 看不见，而「本地少了一个文件」
  在旧的报告里根本不会出现。`remote_added` 在快照为空（首次同步）时刻意不返回 ——
  否则首次同步会变成把整个云端目录下载下来。
- `propagate_remote_delete` 只删「自上次同步未变过」的本地文件；本地改过就保留并说明原因。
- 删云端副本前再次校验 token，且副本数必须恰好为 1（按名字删可能删到别人那份）。
- 三个开关只对 `two-way` 有效，写错变体直接报错，不静默忽略。

**本轮拓出的两个真缺陷（详见 D49）**

1. **并发上传把同一个新目录创建成多份**。rclone 8 路并发，每个 goroutine 都判定
   「目标目录不存在」并各建一个，文件因此被分散；之后按名字解析只命中其中一份，
   其余被报成 `remote-deleted`。真机实测曾出现 4 个同名目录。
   **这条在只读时只是烦人，接到 `propagate_remote_delete` 上就是删掉正常本地文件** ——
   所以给第二期加开关之前必须重验第一期喂给它的信号。修法：`Mkdir` 串行化 + 用新鲜列表复核。
2. **`run --dry-run` 真的删了云端文件**。`--dry-run` 是 rclone 的全局标志，
   只把 rclone 自己那趟变 dry，不传 `job.Options.DryRun`，于是「rclone 那趟说 would copy」
   而「我们自己的删除真的执行」。修法：两个标志任一生效即视为预览。

1. 加一个可选接口，与既有的 `stateFlusher` / `abortHooker`（`job/run.go`）同一模式：

   ```go
   // dirLimmiter 由知道「一个目录最多放多少条」的后端实现。0 表示没有限制。
   type dirLimiter interface {
       MaxChildrenPerDir() int
   }
   ```

2. `job.RunPair` 把预检**移到 `fs.NewFs` 之后**，断言该接口：
   - 后端没有实现 → **完全跳过预检**（local / SMB）
   - 实现了 → 用后端给的值当硬限，再减去余量
3. job 文件增 `[pair.sync] max_nodes_per_dir`，语义需要三态（未设置=用后端默认、
   `0`=显式不限、正数=覆盖），不能沿用现在「0 即默认」的二态。
4. 文案与字段去飞书化：`FeishuLimit` → `BackendLimit`，错误里写后端名。
5. 深度限制（15 层）同样归后端；`PrecheckOptions.MaxDepth` 现在是写死的 15。

**为什么还没动手**

- 用户 2026-11-09 对拆分相关改动的指示是「先不动」
- 移动预检位置会改变错误顺序（先开后端再报超限），属于行为变化
- job 文件新增项要同步 `job/save.go` 的编码器与 `sameSync`（D33 的坑：手写 TOML
  编码器漏字段会静默丢数据），改之前要补字段覆盖测试
