# Contract：state 文件格式

**Feature**: `001-feishu-read-upload` | **Date**: 2026-11-06

> 本文件是 state 文件格式的**唯一权威定义**（宪法原则 IV：单一事实来源）。

---

## 1. 文件位置

| 平台 | 路径 |
|---|---|
| Windows | `%APPDATA%\weftsync\state\<pair-id>.state.json` |
| Linux | `~/.config/weftsync/state/<pair-id>.state.json` |

`<pair-id>` = `sha256(localRoot + "\x00" + remoteRoot)[:16]`（十六进制小写）。
分隔符 `\x00` 防止 `ab` + `c` 与 `a` + `bc` 撞值。

配套文件：
- `<pair-id>.state.json.bak` —— 上一个成功版本
- `<pair-id>.state.json.tmp` —— 写入过程中的临时文件（正常结束后不存在）

---

## 2. 磁盘格式

```
# weftsync state v1  crc32=1a2b3c4d
{"version":1,"pair_id":"a1b2c3d4e5f6a7b8","entries":{"docs/a.xlsx":{"path":"docs/a.xlsx","local_mtime":1793787000,"local_size":102400,"remote_token":"GtflbM301o7vtoxkVANcf5Mknmg","synced_at":1793787100}}}
```

**结构**

| 行 | 内容 | 说明 |
|---|---|---|
| 1 | `# weftsync state v<VER>  crc32=<8位小写十六进制>` | 人类可读；CRC32 覆盖第 2 行起全部字节 |
| 2 | JSON 正文（单行，无缩进） | 便于 CRC 计算与 diff |

**编码**：UTF-8 无 BOM，LF 换行（`\n`），文件末尾有换行。

---

## 3. JSON Schema

```json
{
  "version": 1,
  "pair_id": "string, 16 位十六进制",
  "entries": {
    "<relative-path>": {
      "path": "string",
      "local_mtime": "int64 (Unix 秒)",
      "local_size": "int64 (字节)",
      "remote_token": "string",
      "synced_at": "int64 (Unix 秒)"
    }
  }
}
```

### 3.1 字段约束

| 字段 | 必填 | 约束 |
|---|---|---|
| `version` | 是 | 当前必须为 `1`；读到其他值 → 视为不兼容，进入降级模式 |
| `pair_id` | 是 | 必须与文件名中的 `<pair-id>` 一致；不一致 → 视为损坏 |
| `entries` | 是 | 可以为空对象 `{}` |
| `entries` 的 key | 是 | 必须与 `entries[k].path` 完全相同（冗余但对人工排查有用） |
| `path` | 是 | POSIX 分隔符；无前导 `/`；无尾随 `/`；非空 |
| `local_mtime` | 是 | > 0 |
| `local_size` | 是 | >= 0 |
| `remote_token` | 是 | 非空 |
| `synced_at` | 是 | > 0，仅诊断用，不参与判断 |

### 3.2 校验顺序（读取时）

```
1. 文件存在?                         否 → 降级模式（重建）
2. 第 1 行匹配正则?                  否 → 降级模式
3. 声明的 crc32 与正文实际 crc32 相符? 否 → 尝试 .bak → 仍失败则降级模式
4. 正文是合法 JSON?                  否 → 同上
5. version == 1?                     否 → 降级模式（提示版本不兼容）
6. pair_id 与文件名一致?              否 → 降级模式（提示可能拷错了文件）
7. 遍历 entries，逐条校验字段约束     任一不满足 → 丢弃该条 + 告警（不整体降级）
```

**第 7 步是宽松的**：单条损坏只丢那一条（下次会当作"新增"重新上传），
不影响其余条目的增量判断。

## 4. 写入流程（原子性保证）

```
写 <state>.tmp:
   1. 写第 1 行（占位 crc32=00000000，稍后回填）
   2. 写 JSON 正文，同时用 io.MultiWriter 累积 CRC32
   3. 回填第 1 行的 crc32（Seek(0) 后重写第 1 行）
   4. f.Sync()
   5. f.Close()

提交:
   6. 若 <state> 存在 → 复制为 <state>.bak（覆盖旧 .bak）
   7. os.Rename(<state>.tmp, <state>)

清理:
   8. 失败时删除 <state>.tmp
```

**关键点**

| 步骤 | 为什么 |
|---|---|
| 3 | CRC 必须覆盖最终字节；先写正文再回填头部，避免两遍写正文 |
| 4 | fsync 保证 rename 前数据真正落盘；否则断电后 rename 成功但内容为空 |
| 6 | `.bak` 保存**上一个成功版本**，用于 CRC 失败时回退 |
| 7 | 同目录 rename 原子（POSIX）；Windows 用 `MoveFileEx` 语义 |

### 4.1 节流：不是每传一个文件就重写一遍

快照是**整份重写**的，所以「每上传一个文件就保存一次」是 O(n²) 的写入量。
在真实数据上量过（3,309 个文件、1.16 MB 快照、27 分钟）：实际传输 1.9 GB，
却产生了约 **7.6 GB** 的磁盘写入（因为还有一次 `.bak` 复制），而且每一次写入
都是一次可能丢掉整批记录的机会。

因此写入被节流：**两次保存之间至少间隔 `stateFlushInterval`（默认 15 秒）**。
被节流跳过的保存会置一个 pending 标记，在本轮结束时由 `FlushState()` 强制落盘。

| 情形 | 行为 | 最坏后果 |
|---|---|---|
| 正常运行 | 约每 15 秒落盘一次 | 进程被杀时最后 ≤15 秒的上传记录丢失 → 下轮重传，**不是数据丢失** |
| 一轮结束 | `FlushState()` 忽略节流，把 pending 写完 | — |
| 保存失败 | 保持 pending，之后的 flush 会重试 | 只在整轮都写不进去时才丢，且只导致重传 |

**这条也解释了为什么不能只靠节流**：一次 3 个文件、9 秒的实测里，第 2、3 个
文件都落在节流窗口内。去掉收尾的 `FlushState()`，磁盘上只剩第 1 条记录
（实测：`entries = 1`，恢复后 `entries = 3`）。

### 4.2 重试：rename 会撞上正在扫这个目录的东西

快照通常就放在被同步的目录旁边，而 OneDrive 或杀毒软件会短暂持有目标文件。
实测在 OneDrive 目录里跑 3,309 个文件时，`os.Rename` 反复报
`Access is denied`。

| 操作 | 失败处理 |
|---|---|
| `rename(tmp, state)` | 重试 4 次，退避 20/40/60 ms；仍失败才返回错误 |
| `copyFile(state, state.bak)` | 重试同上；**仍失败则降级为警告并继续** |

`.bak` 失败不阻止主保存：rename 是原子替换，正文不可能写坏，丢掉 `.bak`
只损失「回退一个版本」的能力；而中止保存会丢掉本批全部记录、迫使整轮重传。
两者不对称，故选前者。

**并发**：进程内所有读写都经 `stateMu` 串行化（两个 goroutine 同时写同一个
`.tmp` 会让 rename 失败，实测报「文件正被另一个进程使用」）。跨进程仍按
`<pair-id>.lock` 约定，由调用方保证同一 pair 不被两个进程同时写。

## 5. 降级模式（Read-Only Repair）

**触发条件**（任一）：
- 文件不存在
- 第 1 行格式不符
- CRC 不匹配 且 `.bak` 也失败
- `version` 不为 1
- `pair_id` 与文件名不一致

**行为**

| 动作 | 允许？ |
|---|---|
| 列云端目录 | ✅ |
| 上传新文件 | ✅ |
| **跳过未变化的文件** | ❌ **不能**（没有可信基线，只能全部重传） |
| **删除云端旧 token** | ❌ **绝对禁止** |
| 写新 state | ✅ |

> **"不能跳过"的后果**：降级模式下会把本地全部文件重传一遍，
> 若云端已有同名文件，会新增重复。
>
> **为什么不干脆跳过所有已存在的？** 因为无法区分"云端那份是最新的"
> 和"云端那份是旧的"。宁可多传（可清理）也不误判（会丢数据）。
>
> 用户会看到明确告警：
> ```
> ⚠ state 文件已重建（原因：CRC 校验失败）
>   本次运行不执行任何删除操作。
>   由于缺少可信基线，已上传 N 个文件（可能包含重复）。
>   请在飞书中检查是否有同名重复文件，确认后下次运行将恢复正常增量同步。
> ```

---

## 6. 迁移策略

| 场景 | 处理 |
|---|---|
| 从无到有（首次运行） | 生成新 state，全量上传 |
| `version` 升级（未来 v1→v2） | 读旧版本 → 迁移 → 写新版本；迁移函数按版本号分派 |
| 用户手工删除 state | 降级模式 |
| 用户拷贝别人的 state 过来 | `pair_id` 校验会拒绝 → 降级模式 |
| 本地根路径变更（用户搬家） | `pair_id` 变化 → 生成新 state（旧的不复用，符合预期） |
